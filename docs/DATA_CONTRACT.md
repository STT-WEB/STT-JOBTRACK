## หลักประกันว่าหน้าตาจะไม่เปลี่ยน

แยกเป็น **2 ไฟล์ที่ไม่ยุ่งกัน**:

```
Hub.html      = หน้าตา (CSS + JS + โครงหน้า)  →  แช่แข็ง คัดลอกจาก Mockup v2 ทั้งดุ้น ห้ามแก้
Payload.gs    = ข้อมูล  (อ่านไฟล์จริง → แปลงเป็น JSON รูปแบบเดียวกับ Mockup)
```

จุดต่อเดียวคือบรรทัดนี้ใน `Hub.html`:

```js
const D = <?!= PAYLOAD_JSON ?>;     // Mockup ใช้ข้อมูลสมมติ · ของจริงเสียบ JSON จาก Payload.gs
```

> **แปลว่า:** ถ้า `Payload.gs` คืน JSON หน้าตาเดียวกับที่ Mockup ใช้ → หน้าเว็บจะออกมา**เหมือนเป๊ะ 100%** โดยอัตโนมัติ
> ไม่มีทางเพี้ยน เพราะโค้ดหน้าตาเป็นไฟล์เดียวกันทุกตัวอักษร

**กฎเหล็กของเฟสนี้:** ถ้าข้อมูลจริงไม่พอดีกับหน้าตา → **แก้ที่ Payload.gs เท่านั้น ห้ามแตะ Hub.html**

## ตารางแมป: ทุกฟิลด์ → มาจากไฟล์ไหน คอลัมน์อะไร

### 1. `emps` — ทะเบียนพนักงาน
**แหล่ง:** `STT Jobcost Database-Payroll` → แท็บ **Salary Master**

| ฟิลด์ใน JSON | คอลัมน์จริง |
|---|---|
| `id` | รหัสพนักงาน |
| `name` | ชื่อพนักงาน |
| `dept` | รหัสแผนก |
| `deptName` | แผนก |
| `sub` | ชื่อหน่วยงาน |
| `direct` | `Direct/Indirect (จำนวนคน)` = "Direct" → true |
| `type` | ปรเภทพนักงาน (พนักงานรายเดือน / พนักงานรายวัน) |
| `rate` | อัตรา |
| `salary` | เงินเดือน |
| `benefit` | `**รวมสวัสดิการ` |
| `hireM` / `leaveM` | คำนวณจาก วันเริ่มงาน / วันที่พ้นสภาพ + สถานะพนักงาน (Active / In Active) |

### 2. `rows` — เงินเดือนรายคน-รายเดือน (ต้นทางความจริงของ Payroll)
**แหล่ง:** ไฟล์ `Cal JOB COST <เดือน> 2569` → แท็บ **สรุปตารางเงินเดือน** + แท็บ **PAYROLL_SUMMARY**

| ฟิลด์ | คอลัมน์จริง | จากแท็บ |
|---|---|---|
| `m` | เลขเดือน | สรุปตารางเงินเดือน |
| `id` | รหัสพนักงาน | " |
| `days` | จำนวนวันทำงาน | " |
| `base` | `เงินเดือน+สวัสดิการ` (ไม่รวม OT) | " |
| `p15` / `p30` | OTx1.5 / OTx3 | " |
| `phol` | OTx2 (ชั่วโมงวันหยุด) | " |
| `pot` | Total OT | " |
| `bp` | `**รวมเงินได้ทั้งสิ้น` (BP) | " |
| `otr` | OT Rate | PAYROLL_SUMMARY |
| `hn` | ชม. ปกติจาก Timesheet | " |
| `hhol` | ชม. ทำงานในวันหยุด | " |
| `ot15`,`ot30` | แยกจาก IMP.TIMESHEET ตาม `ประเภทชั่วโมงการทำงาน` | IMP.TIMESHEET_DIRECT |
| `stdH` | ชม. มาตรฐาน | PERFORMANCE |
| `holH` | ชม. หยุดนักขัตฤกษ์ | " |
| `netH` | ชม. มาตรฐานสุทธิ | " |
| `absentH` | ชม. ขาด/ลาจริง | " |
| `th` | ชม. รวมทั้งหมด | " |

> **ด่านตรวจที่ต้องผ่าน:** `base + pot = bp` ทุกบรรทัด · ผลรวม `bp` ของ Direct = ผลรวม `cost` ใน jobRows

### 3. `jobRows` — เวลาที่ลงจ๊อบ (หัวใจของ Job Cost)
**แหล่ง:** ไฟล์ Cal → แท็บ **JOB_COST_DIRECT** (รวมยอดต่อ คน × เดือน × จ๊อบ × process)

| ฟิลด์ | คอลัมน์จริง |
|---|---|
| `m` | จาก วันที่ทำงาน → งวด |
| `id` | รหัสพนักงาน |
| `job` | JOB CODE |
| `proc` | Process |
| `hn` / `ot15` / `ot30` / `hhol` | แยกตาม `ประเภทชั่วโมง` (1 / 3 / 4 / 2) |
| `th` | จำนวนชั่วโมง (รวม) |
| `cost` | ต้นทุนค่าแรง |

### 4. `recon` — Reconcile 2 ตัว
**แหล่ง:** โฟลเดอร์ **Time Bplus** (รายเดือน) + `JOBTRACK_Job_Log 2026`

| ฟิลด์ | ที่มา |
|---|---|
| `bplus` | ชั่วโมงรวมของคนนั้นในไฟล์ Bplus เดือนนั้น |
| `jt` | ชั่วโมงรวมจาก Job_Log (คอลัมน์ `ชม.คิดค่าแรง` หรือ `ชม.รวม` แล้วแต่รุ่น) |
| `diff` | `bplus − jt` |
| `c` | ดัชนีสาเหตุ (ดูตาราง "กฎเดาสาเหตุ" ด้านล่าง) |

> ⚠️ **JOBTRACK เปลี่ยนคอลัมน์มา 4 รุ่นในปีเดียว** → ต้องอ่านด้วย **ชื่อหัวคอลัมน์** ไม่ใช่ตำแหน่ง
> Column Map: `ชม.คิดค่าแรง` → ถ้าไม่มีใช้ `ชม.OT ทศนิยม + ชม.ปกติ ทศนิยม` → ถ้าไม่มีอีกใช้ `ชม.รวม`

**กฎเดาสาเหตุ (ระบบตรวจตามลำดับ):**

| ลำดับ | เงื่อนไขที่ตรวจ | สาเหตุที่แสดง |
|---|---|---|
| 1 | มีแถวใน Job_Log ที่ `เวลาออก` ว่าง / `สถานะ` ≠ Check Out | ลืม Check Out |
| 2 | ไม่มีรหัสพนักงานนี้ในไฟล์ Bplus | ไม่ได้สแกนนิ้ว |
| 3 | มี 2 แถวขึ้นไปที่ช่วงเวลาทับกัน | ลงจ๊อบซ้อนเวลา |
| 4 | `ประเภทชั่วโมง` ไม่ตรงกับ `ประเภทวันทำงาน` ในปฏิทิน | ประเภทชั่วโมงผิด |
| 5 | วันหยุดนักขัตฤกษ์ในปฏิทิน ≠ ที่ Payroll ใช้ | ปฏิทินไม่ตรง |
| 6 | ไม่เข้าข้อไหนเลย | ยังระบุไม่ได้ — เปิดใบลงเวลาจริงดู |

### 5. `perf` — Performance
**แหล่ง:** ไฟล์ Cal → แท็บ **PERFORMANCE** (ยกตัวเลขมา) แต่ **คำนวณเกรดใหม่**

```
pct   = ชม.ปกติจาก Timesheet ÷ ชม.มาตรฐานสุทธิ × 100
grade = A+ ≥95 · A 90–94.99 · B 85–89.99 · C 80–84.99 · D 75–79.99 · F <75
cph   = (เงินเดือน+OT+สวัสดิการ) ÷ ชม.รวมทั้งหมด
```
> เกรดในไฟล์เดิม**ห้ามยกมาใช้** (ของเดิมให้ A+ ทุกคนที่ไม่ขาดงาน) — ให้ระบบคิดใหม่ตามช่วงที่เบียร์เคาะ

### 6. `alloc` — Allocate Indirect
**ระบบคำนวณเอง** (ไม่มีในไฟล์ไหนเลย):

```
pool  = ผลรวม bp ของพนักงาน Indirect ในเดือนนั้น
hours = ผลรวม th ของ jobRows ในเดือนนั้น
rate  = pool ÷ hours
byJob[j] = rate × (ชั่วโมง Direct ของจ๊อบ j)     // จ๊อบสุดท้ายรับเศษ ให้รวมกลับได้เท่า pool เป๊ะ
```

### 7. `jobs` — Master รายจ๊อบ
**แหล่ง:** 3 ไฟล์ประกอบกัน ผูกด้วย **Job Code**

| ฟิลด์ | ไฟล์ / คอลัมน์ |
|---|---|
| `code`,`name`,`type` | Jobcost Master/Dashboard 2026 → `Job Code`, `ชื่องาน`, `ประเภทงาน` |
| `cust` | Payroll DB → `custName` (จับคู่ DocuNo = Job Code) |
| `byMonth` | Master/Dashboard → คอลัมน์ ม.ค.–ธ.ค. |
| `carry` | Master/Dashboard → `ยอดยกมา` |
| `sttLabor` | Master/Dashboard → `รวมค่าแรง STT` |
| `sub` | Master/Dashboard → `ค่าแรงผู้รับเหมา` (ต้นทางคือ `SUM ของ GoodAmnt` ต่อ JobCode) |
| `indirect` | จาก `alloc` (ระบบคำนวณ) |
| `total` | `carry + sttLabor + indirect + sub` |
| **`estBudget`** | **Payroll DB → `Budget labour` (จับคู่ DocuNo)** ← ต้องให้เบียร์ยืนยัน |
| **`saleBudget`** | **Payroll DB → `SUM ของ billaftrDiscAmnt`** ← ต้องให้เบียร์ยืนยัน |
| `varBudget` / `pctBudget` | คำนวณ |
| `start`,`due`,`progress` | Cal → แท็บ **ALL WIP** (`START DATE`, `LATEST DATE DELIVERY`, `TOTAL PROGRESS`) |
| `leadDays` | `due − start` (วัน) |

> Master/Dashboard มีคอลัมน์ `Est. Budget` · `Sale Budget` · `ส่วนต่าง Budget` · `% Cost/Budget` · `สถานะ` **ว่างอยู่**
> → ระบบจะ **เขียนกลับ (write-back)** ค่าเหล่านี้ลงไฟล์ให้ เพื่อให้ไฟล์ Excel เดิมกับเว็บตรงกันเสมอ

### 8. `procRows` — เจาะราย Process
**แหล่ง:** ไฟล์ Cal → แท็บ **JOB_COST_PROCESS_SUMMARY** (JOB CODE, Process, ชม.ปกติ/OT/วันหยุด/รวม, จำนวนพนักงาน, ต้นทุน Direct รวม, ต้นทุนเฉลี่ย/ชม.)

| ฟิลด์ | คอลัมน์จริง |

| `heads` | จำนวนพนงที่จ่าย |
| `salary` | เงินเดือน |

| `ot` | OT |

## ก. โครงแผนกของจริง (แก้จากตารางข้อ 1 ด้านบน)

ไฟล์จริงใช้ **รหัส 4 หลัก 2 ชั้น** — ที่เขียนไว้ตอนแรกสลับกัน ของจริงคือ:

| ฟิลด์ใน JSON | คอลัมน์จริง | ตัวอย่าง |
|---|---|---|
| `dept` (แผนกใหญ่) | **รหัสหน่วยงาน** | 1000 HR&ADMIN · 3000 DESIGN · 4000 AFTER SALE · 5000 PRODUCTION |
| `deptName` | **ชื่อหน่วยงาน** | PRODUCTION |
| `subCode` | **รหัสแผนก** | 1001 · 5002 · 5013 · **5018** |
| `sub` | **แผนก** | F0 PART & MARKCUT · F1 FABICATION · F5 ELECTRIC · KEMREX |
| `direct` | `Direct/Indirect (จำนวนคน)` | "Direct" / "Indirect" (มีคอลัมน์ `Direct/Indirect (%)` = "Direct 70%" ด้วย) |

**KEMREX = รหัสแผนก 5018** (เบียร์ยืนยัน) แต่ในไฟล์จริง **5018 อยู่ใต้หน่วยงาน 5000 PRODUCTION**
เบียร์ต้องการเห็น KEMREX เป็นแผนกใหญ่แยกออกมา → ทำที่ `CFG.KEMREX_SPLIT = true` ใน `Payload.gs`
(ยกขึ้นเป็นแผนกใหญ่ตอนสร้าง JSON — **ไม่แตะ Hub.html และไม่แก้ไฟล์ต้นทาง**) ปิดได้ด้วยการตั้งเป็น `false`

## ข. ไฟล์ Cal รายเดือน — ชื่อไฟล์ไม่เป็นระเบียบ

โฟลเดอร์ Cal มีชื่อไฟล์ **2 แบบปนกัน** และมีทั้งรุ่นเก่า/รุ่นใหม่:

| เดือน | ไฟล์ที่ระบบเลือกใช้ |
|---|---|
| 1 | `1. Cal JOB COST JANUARY 2026 (NEW)` |
| 2 | `2. Cal JOB COST FEBRUARY 2026 (NEW)` |
| 3–7 | `N. DATA JOB COST <MONTH> 2026 (NEW)` |
| 8 | **ยังไม่มีไฟล์** |

กติกาที่ `calFiles_()` ใช้: ชื่อมีคำว่า `JOB COST` · ขึ้นต้นด้วย `เลขเดือน.` · **ถ้ามีทั้งรุ่นเก่าและ (NEW) เลือก (NEW)** · ถ้าซ้ำอีกเลือกไฟล์ที่แก้ล่าสุด
→ `CFG.NMONTH` **ไม่ต้องตั้งเอง** ระบบนับจากไฟล์ที่มีจริง (ตอนนี้ = 7 ไม่ใช่ 8)

## ค. โครงแท็บในไฟล์ Cal (ตรวจจากไฟล์เดือน 7)

| แท็บ | คอลัมน์ที่ระบบใช้ |
|---|---|
| `ALL WIP` | ประเภทงาน · JOB CODE · JOB NAME · START DATE · LATEST DATE DELIVERY · TOTAL PROGRESS |
| `ปฏิทินวันทำงาน` | วันที่ · ประเภทวันทำงาน · **PeriodKey_รายเดือน** (`2026-07`) → นับวันทำงาน/วันหยุดต่อเดือน |
| `WORK_HOUR_TYPE` | Work Hour Type Name · Multiplier → `hourTypes` |
| `สรุปตารางเงินเดือน` | เลขเดือน · รหัสพนักงาน · จำนวนวันทำงาน · **OTx1 / OTx1.5 / OTx2 / OTx3 / Total OT** |
| `PAYROLL_SUMMARY` | **(เงินเดือน+OT+สวัสดิการ) = BP** · (เงินเดือน+สวัสดิการ ไม่รวม OT) · Total OT · OT Rate · ชม. ปกติจาก Timesheet · ชม. ทำงานในวันหยุด · ชม. ขาด/ลาจริง |
| `JOB_COST_DIRECT` | วันที่ทำงาน · รหัสพนักงาน · JOB CODE · Process · **ประเภทชั่วโมง** · จำนวนชั่วโมง · ต้นทุนค่าแรง |
| `PERFORMANCE` | ชม. มาตรฐาน · ชม. หยุดนักขัตฤกษ์ · ชม. มาตรฐานสุทธิ · ชม. ปกติจาก Timesheet · ชม. รวมทั้งหมด · ชม. ขาด/ลาจริง (เกรดในไฟล์ **ไม่ใช้** — คิดใหม่) |

**ประเภทชั่วโมง** อ่านจากเลขนำหน้า: `1.`→ชั่วโมงปกติ · `2A.`→ทำงานวันหยุด · `3.`→OT ปกติ · `4.`→OT วันหยุด

**ที่มาของตัวเลขแต่ละก้อน (สำคัญ — เป็นตัวการันตีว่าด่านตรวจผ่าน):**

* ยอดเงิน (`bp`, `base`, `pot`) → มาจาก **PAYROLL_SUMMARY เท่านั้น** และถ้า `base + pot ≠ bp` ระบบจะบังคับ `base = bp − pot` → ด่านตรวจข้อ 1 ผ่านเสมอ
* ชั่วโมงของพนักงาน **Direct** → มาจาก **JOB_COST_DIRECT** (ตัวเดียวกับที่ลงจ๊อบ) → ด่านตรวจข้อ 3 ผ่านเสมอ
* ชั่วโมงของพนักงาน **Indirect** → มาจาก PAYROLL_SUMMARY (ไม่ได้ลงจ๊อบ)
* `p15` = `Total OT − OTx2 − OTx3` (กลืน OTx1 เข้ามา) → ค่าแรง OT รวมเท่ากับที่จ่ายจริงเสมอ

## ง. Process — ของจริงมี 38 ชื่อ ไม่ใช่ 6

Mockup มี 6 process (A–F) แต่ไฟล์จริงเดือนเดียวมี **38 ชื่อ** ("ทำปลายแหลม", "Install Electrical", "พับชิ้นงาน", ...)
ถ้ายัดทั้ง 38 เข้ากราฟ กราฟจะพัง (จานสีมี 8 ช่อง)

→ ใช้กติกาเดียวกับที่ตกลงกันไว้เรื่องแผนก: **7 อันดับแรกตามค่าแรงแยกสี (P1–P7) ที่เหลือรวมเป็น "อื่นๆ" (PX)**
ปรับจำนวนได้ที่ `CFG.NPROC` (สูงสุด 7 เพราะจานสีมี 8 ช่อง) — **หน้าตาไม่เปลี่ยน**

## จ. Est. Budget / Sale Budget

เบียร์ยืนยัน: **ยังไม่มี Est. Budget มีแต่ Sale Budget**

ไฟล์ Payroll DB มีคอลัมน์เงินต่อจ๊อบ 2 ตัว ซึ่ง**คนละกลุ่มจ๊อบกัน** (ไม่ทับกันเลย):

| คอลัมน์ | กลุ่มจ๊อบ | จำนวน | ช่วงตัวเลข |
|---|---|---|---|
| `Budget labour` | **JT** (ถังใหม่) | 206 แถว | 160,000 – 425,887.85 |
| `SUM ของ billaftrDiscAmnt` | **JM / JMI** (งานบริการ) | 206 แถว | 700 – 50,000 |

ระบบทำไว้แบบนี้ (แก้ได้ที่ `buildJobs_` บรรทัดเดียว):

```
estBudget  = 0                                   // ปล่อยว่างตามความจริง
saleBudget = billaftrDiscAmnt  ถ้าไม่มี → Budget labour
ส่วนต่าง / % Cost/Budget = เทียบกับ Sale Budget   // จนกว่าจะมี Estimate จริง
```

> ⚠️ **ข้อเดียวที่ยังอยากให้เบียร์ยืนยัน:** สำหรับงาน **JT** ตัวที่เบียร์เรียกว่า "Sale Budget" คือ `Budget labour` ใช่ไหม
> (เช่น JT-62/0135 = 425,887.85) หรือ Sale Budget ของ JT อยู่ไฟล์อื่น — บอกมาบรรทัดเดียว แก้ 1 บรรทัด

## ฉ. ไฟล์ Time Bplus — เห็นของจริงแล้ว (ปลดล็อก Reconcile)

โฟลเดอร์ Bplus มี **7 ไฟล์ที่แปลงเป็น Google Sheets แล้ว** (`1.Time Bplus 26/12/2569 To 25/01/2569` … เดือน 7)
งวดจ่าย = **26 เดือนก่อน → 25 เดือนนี้** ตรงกับที่ตั้งไว้ใน `CFG.PERIOD_START`

คอลัมน์จริง (รายวัน ต่อคน):
`สาขา · แผนก · รหัส · ชื่อพนักงาน · เวลารูดบัตร · หมายเหตุ · รหัสกะ · วันที่ · ชม.งาน · มาสาย · กลับก่อน · OTx1 · OTx1.5 · OTx2 · OTx3 · ขาดงาน · ลาป่วยมี · ป่วยไม่มี · พักร้อน · กิจหัก · กิจไม่หัก · ลาอื่นๆ · อาหาร · ลืมรูดบัตร`

**กฎเดาสาเหตุที่ระบบใช้จริง** (`buildRecon_`) — ไล่ตามลำดับ:

| ตรวจอะไร | สาเหตุที่ขึ้นจอ |
|---|---|
| ไม่มีไฟล์ Bplus เดือนนั้น / ไม่มีรหัสคนนี้ในไฟล์ | **ไม่ได้สแกนนิ้ว** (c=1) |
| `ลืมรูดบัตร` > 0 หรือ `เวลารูดบัตร` มีเวลาเดียว (เข้าอย่างเดียว) | **ลืม Check Out** (c=0) |
| `ขาดงาน` > 0 หรือมีวันลา | **ปฏิทิน/วันลาไม่ตรง** (c=4) |
| ชั่วโมง JOBTRACK > ชั่วโมง Bplus | **ลงจ๊อบซ้อนเวลา** (c=2) |
| นอกนั้น | **ประเภทชั่วโมงผิด** (c=3) |

เดือนที่ยังไม่แปลงไฟล์ → ระบบขึ้น "ไม่ได้สแกนนิ้ว / เทียบไม่ได้" ตามจริง ไม่เดาตัวเลขให้

## ช. เรื่องเทคนิคที่ต้องรู้ (กันพัง)

1. **Apps Script ใช้ตัวแปร global ร่วมกันทุกไฟล์** — โปรเจกต์เดิมมี `num_()` และ `readSheet_()` อยู่แล้วใน `Cal.gs`/`Code.gs`
   ของใหม่จึงเปลี่ยนชื่อเป็น `nvNum_()` / `nvReadSheet_()` **ห้ามเปลี่ยนกลับ** ไม่งั้นระบบเดิมพัง
2. `.claspignore` เป็นแบบ whitelist → เพิ่ม `!Payload.gs` แล้ว ไม่งั้น clasp จะไม่อัปไฟล์ขึ้นไป
3. `doGet()` ใน `WebApp.gs` เปลี่ยนจาก `createHtmlOutputFromFile` → `createTemplateFromFile` เพื่อเสียบ JSON เข้าหน้า
4. `CFG.CACHE_KEY` ต้องบั๊มทุกครั้งที่แก้ logic (ตอนนี้ `NOVA_PAYLOAD_v3_1_0`) หรือเรียก `forceRefresh()`
5. **`probe()`** — รันในหน้า Apps Script Editor ก่อน deploy จะพิมพ์ชื่อแท็บทั้งหมด · แท็บที่หาไม่เจอ · และผลด่านตรวจ 8 ข้อ
